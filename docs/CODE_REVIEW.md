# SteamChat code review

Scope: SteamChat-authored code only — `steamchat-domain/src/`, `steamchat-steamkit/src/`,
`TMessagesProj/src/main/kotlin/org/steamchat/`. Upstream `org/telegram/**` was read only where it
was needed to ground a claim about our code (`BaseFragment`, `ActionBarLayout`, `BackupAgent`).
JavaSteam 1.8.0 behaviour (`SteamUser.logOff`, `CMClient.send`, `CallbackManager.subscribe`) was
verified by disassembling the jar, not assumed.

Every row below points at code that was actually read. Findings that could not be verified against
real bytecode or real call sites were dropped rather than guessed at.

## Verified clean

Checked deliberately and found genuinely fine — listed so these are not re-reviewed:

- **Boundary discipline (master prompt §7).** `steamchat-domain/.../SteamService.kt` imports only `kotlinx.coroutines` and `org.steamchat.domain`; no JavaSteam, protobuf, callback or Android type crosses the interface. `steamchat-domain/build.gradle` has exactly one dependency (`kotlinx-coroutines-core`) — zero Android, zero `org.telegram.*`. The JavaSteam types stay inside `steamchat-steamkit`, and `SteamMapping.kt` is the only translation point.
- **`SteamMapping.kt:6-21`.** `EPersonaState → SteamStatus` handles the `null` receiver and folds `Invisible` into `OFFLINE` with a comment explaining why; `avatarUrl` correctly rejects `null`, empty and all-zero hashes before hex-encoding, and `%02x` is the right format for signed bytes. All three behaviours are covered by `SteamMappingTest.kt:11-32`.
- **No credential ever reaches a log.** `grep` for `Log.`, `println`, `System.out`, `printStackTrace` and `FileLog` across all three areas returns zero hits, and nothing registers a JavaSteam `LogManager` listener or an `IDebugNetworkListener`, so the library's own debug logging is inert. The one place a credential could plausibly escape — `SteamLoginResult.Failure(e.message ?: e.toString())` at `JavaSteamService.kt:134` — carries an exception message, not the password. (The in-memory retention issue is #6; that is a heap concern, not a log concern.)
- **`EncryptedSessionStore.kt:13-48`.** Correct `MasterKey` + `AES256_SIV`/`AES256_GCM` scheme, holds `ApplicationLoader.applicationContext` (not an Activity, so no context leak), `by lazy` defaults to `SYNCHRONIZED` so there is no double-init race, and it persists only `username` + `refreshToken` — never the password, exactly as the class doc claims. I specifically checked the Android auto-backup exfiltration path: the app declares `android:backupAgent=".BackupAgent"` and `BackupAgent.java:13` registers a `SharedPreferencesBackupHelper` for only `saved_tokens` and `saved_tokens_login`, so `steamchat_session` is not backed up off-device. Not a finding.
- **`JavaSteamService` history round-trip cannot deadlock.** `getMessageHistory:287-299` is bounded by `withTimeoutOrNull(5000L)` and removes its `pendingHistoryRequests` entry on both the callback path (`:221`) and the timeout path (`:295`), so that map does not leak. (The `historyLoaded` set does — that is #9, a separate collection.)
- **`AtomicLong nextMessageId` (`:75`) and the `ConcurrentHashMap` map objects.** Correct choice for cross-thread id allocation and for the map-level operations; `getOrPut` on a `ConcurrentHashMap` is safe enough at this scale. The bug is the unguarded `MutableList` *values* (#4), not the maps.
- **`SteamUser.logOff()` really does end the pump in the happy path.** Disassembled `SteamUser.class`: `logOff()` calls `setExpectDisconnection(true)` then `client.disconnect()`, so the resulting `DisconnectedCallback.isUserInitiated` is `true` and `JavaSteamService.kt:141-143` correctly takes the `isRunning = false` branch rather than the reconnect branch. The teardown logic at `:140-149` is right; it is only the *rejected-logon* path that never reaches it (#1).
- **Domain models.** `SteamUser`, `SteamDialog`, `SteamMessage`, `SteamStatus` are immutable `data class`/`enum` with no behaviour, safe to hand across threads. `SteamMessage.kt:3-7` documents the locally-assigned id/timestamp constraint accurately (which is what makes #10 diagnosable).
- **`FakeSteamService` matches its spec.** 5 friends, 3 dialogs, 50 messages, 2 unread (`:26-61`) — asserted by `FakeSteamServiceTest.kt:10-25`, and the arithmetic checks out by hand. Its only real divergences from the JavaSteam implementation are noted in #5 and #7.
- **`SteamMessageCell.kt:53-74`.** Re-reads all `Theme` colours per bind and correctly flips bubble gravity and the in/out colour keys — the right pattern; it is `SteamDialogCell` that deviates (#20).
- **`SteamDebugActivity.kt:26-33`.** The `ActionBarLayout(this, false)` comment is accurate: `main=false` genuinely avoids the `LaunchActivity.instance` dependency in the BottomSheetTabs path. Good, correctly-explained workaround.
- **Gradle wiring.** `settings.gradle:10-11` and `TMessagesProj/build.gradle:86-87` declare both modules; `steamchat-steamkit` using `implementation project(':steamchat-domain')` does not hide domain types from the UI because `TMessagesProj` depends on `:steamchat-domain` directly. No missing-transitive problem.
