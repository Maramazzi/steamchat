# SteamChat

Нативный Android-клиент Steam-чата, построенный на форке официального Telegram Android
(DrKLO/Telegram) как UI-базе, с полностью заменённым бэкендом: вместо MTProto — Steam
через JavaSteam. Полное ТЗ: `SteamChat_master_prompt.md`.

**Общайся с пользователем по-русски.**

---

## 1. Рабочие правила этой сессии

### Скриншоты и визуальная проверка — делегировать пользователю

Не гоняйся за скриншотами эмулятора. Это уже съело много времени: сплэш-экран,
ripple-эффект и иконки лаунчера — переходные/кэшируемые состояния, которые `adb screencap`
ловит ненадёжно.

**Правильно:** собери, установи, запусти — и **спроси пользователя одним вопросом**, что он
видит на экране (используй `AskUserQuestion` с конкретными вариантами ответа). Пользователь
сам смотрит на эмулятор и отвечает — это на порядок быстрее и надёжнее.

Скриншот делай только если пользователь прямо попросил или нужно зафиксировать статичный
экран, который точно не меняется.

### Проверять, а не гадать

Все крупные баги в этом проекте находились запуском, а не чтением кода. Перед тем как
утверждать, что API существует — проверь его в исходниках/JAR. Не выдумывай сигнатуры
методов JavaSteam или Telegram.

### Не форкать монолиты Telegram

`ChatMessageCell` — 29 500 строк / 340 обращений к TLRPC, `DialogCell` — 6 500 строк, их
delegate-методы типизированы прямо `TLRPC.User`. Форкать их нельзя. Вместо этого
переиспользуем инфраструктуру рендера (`Theme`, `BackupImageView`, `AvatarDrawable`,
`Theme.getSelectorDrawable()`) в своих компактных ячейках под наши доменные типы —
`SteamDialogCell` / `SteamMessageCell` уже сделаны так.

## 2. Архитектура

```
UI (org.steamchat.ui, Kotlin, внутри TMessagesProj)
        |   использует UI-примитивы Telegram (Theme/BaseFragment/BackupImageView)
        v
steamchat-domain      чистый Kotlin/JVM: модели + SteamService + SessionStore + FakeSteamService
        ^ реализует
steamchat-steamkit    JavaSteamService поверх библиотеки JavaSteam (JVM-порт SteamKit2)
        v
Steam CM servers
```

**Почему три модуля, а не один:**

- `TMessagesProj` сидит на Java 8 / minSdk 21, а JavaSteam требует Java 17 → Steam-слой
  вынесен отдельно, чтобы не тащить апгрейд Java на весь телеграмный код.
- `steamchat-steamkit` отделён от `steamchat-domain`, чтобы тяжёлые зависимости
  (javasteam, bouncycastle) не текли в потребителей домена и юнит-тесты.
- Через границу `SteamService` **не должен проходить ни один тип SteamKit2/JavaSteam** —
  только доменные модели (раздел 7 ТЗ).

**Ключевые файлы:**

| Файл | Роль |
|---|---|
| `steamchat-domain/.../service/SteamService.kt` | Контракт бэкенда (login, resumeSession, flows) |
| `steamchat-domain/.../service/FakeSteamService.kt` | Фейк для UI без Steam-аккаунта |
| `steamchat-steamkit/.../JavaSteamService.kt` | Реальный бэкенд, вся логика колбэков Steam |
| `TMessagesProj/src/main/kotlin/org/steamchat/ui/SteamDebugActivity.kt` | Точка входа, хост ActionBarLayout |
| `TMessagesProj/src/main/kotlin/org/steamchat/ui/SteamServiceHolder.kt` | Синглтон сервиса (заменить на DI позже) |

## 3. Сборка и запуск (проверенные команды)

```bash
# Компиляция нашего Kotlin (быстро, ~10с) — основная проверка при итерациях
JAVA_HOME="/c/Program Files/Android/Android Studio/jbr" ./gradlew :TMessagesProj:compileDebugKotlin

# Юнит-тесты доменного слоя и адаптера
JAVA_HOME="/c/Program Files/Android/Android Studio/jbr" ./gradlew :steamchat-domain:test :steamchat-steamkit:test

# Полный APK (~2 мин; нативная часть закэширована)
JAVA_HOME="/c/Program Files/Android/Android Studio/jbr" ./gradlew :TMessagesProj_App:assembleAfatDebug
```

APK: `TMessagesProj_App/build/outputs/apk/afat/debug/app.apk`
Package: `org.telegram.messenger.beta` · Activity: `org.steamchat.ui.SteamDebugActivity`

```bash
SDK="$LOCALAPPDATA/Android/Sdk"; ADB="$SDK/platform-tools/adb.exe"
"$ADB" install -r TMessagesProj_App/build/outputs/apk/afat/debug/app.apk
"$ADB" shell am force-stop org.telegram.messenger.beta
"$ADB" shell am start -n org.telegram.messenger.beta/org.steamchat.ui.SteamDebugActivity
"$ADB" logcat -d -b crash | tail -30      # проверка краша
```

Эмулятор: AVD **`Spike36`** (API 36).

```bash
nohup "$SDK/emulator/emulator.exe" -avd Spike36 -no-snapshot -no-boot-anim > /tmp/emu.log 2>&1 &
```

## 4. Грабли, на которые уже наступали (не наступать снова)

| Проблема | Причина и решение |
|---|---|
| **Холодный старт ~18 сек** на эмуляторе | Это не зависание. `ApplicationLoader` Telegram грузит всё своё. В логах: `ActivityTaskManager: Displayed ... +17s794ms`. Не диагностировать как краш. |
| Эмулятор API 24 — `CertPathValidatorException` | Устаревший список корневых сертификатов в старом образе. Тестировать **только на Spike36 (API 36)**. Это не баг JavaSteam. |
| Jetifier падает на `bcprov-jdk18on` | Байткод Java 25 новее, чем понимает ASM внутри Jetifier. Решено: `android.jetifier.ignorelist=bcprov-jdk18on` в `gradle.properties`. |
| Дубликат `META-INF/versions/9/OSGI-INF/MANIFEST.MF` | Три jar кладут файл по одному пути. Решено: `packagingOptions.exclude` в `TMessagesProj_App/build.gradle`. |
| `ActionBarLayout` — NPE в `addFragmentToStack` | Конструктор не инициализирует `fragmentsStack`. Нужен явный `setFragmentStack(ArrayList())`. |
| `ActionBarLayout(ctx, main=true)` — NPE | `main=true` включает BottomSheetTabs, который жёстко лезет в статический синглтон `LaunchActivity.instance`, которого у нас нет. Использовать `main=false`. |
| Белый экран без выхода по кнопке «назад» | Закрытие последнего фрагмента опустошало стек. Решено: `needCloseLastFragment()` вызывает `finish()`, когда в стеке ≤1 фрагмент. |
| **Тёмная тема ломает виджеты** | Системные виджеты (EditText, hint, Button) берут цвета из темы Activity, а не из `Theme.getColor()`. Родитель темы обязан быть тёмным **и в `values/`, и в `values-v31/`** — иначе на API 31+ тихо откатывается на светлую, и текст становится тёмным на тёмном. Свои View красить явно. |
| **`BUILD SUCCESSFUL`, а установленный APK — старый** | Убрал строку кода, `compileDebugKotlin` пересобрался и подтверждён (`javap` по свежему `.class` в `build/tmp/kotlin-classes/` — байткода строки уже нет), а на эмуляторе изменение не появилось: обычный `assembleAfatDebug` (без `--rerun-tasks`) отрапортовал `BUILD SUCCESSFUL`, но `adb install -r` поставил APK, в котором старая View всё ещё живая (проверено `uiautomator dump` — лишний `View` 1dp как был). Обычные Gradle up-to-date проверки на упаковочных тасках (`dexBuilder*`/`mergeProjectDex*`/`packageAfat*`) иногда не замечают, что нужно перепаковать, если между вызовами меняется только код, а не структура модулей — конкретный триггер не выяснен. Решено `--rerun-tasks` на `assembleAfatDebug` (94/94 таска реально выполнились, не «UP-TO-DATE») — после этого лишний `View` пропал и из дампа, и с экрана. Если правка кода не отражается на эмуляторе, а компиляция «зелёная» — не тратить время на догадки про сам код, сразу `--rerun-tasks` на сборку APK. |
| **Иконка-«мыло» на сплэше** | `windowSplashScreenAnimatedIcon` указывал на mipmap максимум 192px, а сплэш рендерится в 288dp (~756px) → апскейл ×4. Решено: отдельный ассет `drawable-nodpi/ic_steamchat_splash.png` 1024px. |
| Иконка лаунчера показывала Telegram | Adaptive-icon XML ссылался на `@mipmap/ic_launcher_steamchat` — **то же имя, что у самого XML** → циклическая ссылка, тихий откат на иконку приложения. Foreground обязан иметь отдельное имя (`..._foreground`). |
| Adaptive-иконка обрезается | Маска режет до центральных ~2/3. Логотип должен быть вписан в 66% канвы. Нет закоммиченного генератора — обработка исходника (`herochat.png`, 1024px) в 5 плотностей mipmap + сплэш каждый раз одноразовый скрипт (Pillow: `pip install pillow`, флэт-иконка — прямой ресайз всего исходника, adaptive-foreground и сплэш — исходник уменьшен до 66% канвы и вставлен по центру на прозрачный фон; round-варианты у существующих ассетов побайтово идентичны non-round, отдельно не считать). |
| `adb pull` из Git Bash | Пути ломаются. Использовать `MSYS_NO_PATHCONV=1` и `//sdcard/file.png` (двойной слэш). |
| `adb shell input tap x y` не долетает до верхних кнопок ActionBar | На Spike36 статус-бар занимает `statusBars:[0,63,0,0]` (см. `WindowInsets changed` в logcat) — тап с y меньше ~63 перехватывает системный статус-бар, а не наше View, даже если по `uiautomator dump` элемент кликабелен и его bounds начинаются с 0. Тапать по ActionBar на y ≥ 100. Быстрая проверка перед тем как чинить код: `adb shell uiautomator dump` + сверить bounds, а не сразу подозревать код. |
| **Полностью чёрный экран, видны только аватарки** | `core.autocrlf=true` (глобальный git на Windows) переписал LF→CRLF в `assets/*.attheme` при checkout. Парсер `Theme.getThemeFileValues()` режет только `\n`, `\r` остаётся в значении → `Integer.parseInt("-14606047\r")` кидает → **все 483 цвета темы молча становятся 0** → чёрное на чёрном. Апстрим не видит бага, потому что собирается на Linux. Решено: `.gitattributes` с `TMessagesProj/src/main/assets/** -text`. Пострадали были и GLSL-шейдеры. Проверка: `git ls-files --eol -- 'TMessagesProj/src/main/assets/*'` — не должно быть `w/crlf`. |
| **Системный статус-бар наезжает на нашу шапку** | Та же семья, что чёрный экран ниже: `AndroidUtilities.statusBarHeight` заполняется в `DrawerLayoutContainer.onApplyWindowInsets`, то есть внутри `LaunchActivity`, которую `SteamDebugActivity` обходит. Оставшись 0, она ломает `ActionBar.onMeasure` — его высота это `actionBarHeight + (occupyStatusBar ? statusBarHeight : 0)`, поэтому места под статус-бар не резервируется вообще. При `targetSdkVersion 36` edge-to-edge включён принудительно, и подложить отступ больше некому. Решено: свой `ViewCompat.setOnApplyWindowInsetsListener` на `actionBarLayout` — выставляет `statusBarHeight`/`navigationBarHeight` через готовый `AndroidUtilities.getDefaultWindowInsets()` (не свой разбор инсетов) и padding снизу под жестовую полосу, иначе панель ввода чата и панель звонка уезжают под неё. |
| Аватарки рисуются, но экран чёрный (NPE `Paint.setShader`) | Отдельная от CRLF проблема: `SteamDebugActivity` не проходит через `LaunchActivity`, поэтому общие `Paint` не создавались и `AvatarDrawable.draw()` кидал NPE на каждый кадр. Решено: `Theme.createDialogsResources(this)` + `Theme.createChatResources(this, false)` в `onCreate` (так же делают `BubbleActivity`/`ExternalActionActivity`). |
| **Приложение при обычном использовании открылось в регистрации Telegram** | Живой баг у пользователя, не гипотетический. Причина — не крашем, а тем, что в манифесте жил второй, полностью рабочий вход в приложение: `activity-alias android:name="DefaultIcon" android:enabled="true"`, указывающий на `LaunchActivity` (настоящий телеграмный онбординг) — независимо от нашего `SteamDebugActivity`, тоже с `LAUNCHER`. Какую из двух Android откроет при восстановлении задачи/из недавних — не гарантировано. Аудит манифеста вскрыл целый пласт таких же живых Telegram-точек входа помимо иконки: `tg://`/`t.me`/`telegram.me` deep links с `BROWSABLE` (наше приложение могло перехватить чужую телеграмную ссылку), share-таргеты (`ACTION_SEND` картинок/видео/текста — вели в MTProto-UI, которого эффективно нет), алиас `CallsActivity`, `ShareActivity` (`tgb://`), виджеты рабочего стола (`Chats`/`ContactsWidget*`), Google Assistant-интеграция в `TMessagesProj_App/AndroidManifest.xml`. Решено вырезать **из манифеста** (не удалять исходники — see раздел «упоминаний в других файлах» ниже): все 6 alias'ов иконок, `CallsActivity`, `ShareActivity`, виджеты и их сервисы, весь набор intent-filter'ов на самой `LaunchActivity` (deep links, share, `CREATE_STICKER_PACK`, контакт-профиль, `tonsite`), Google Assistant-блок. Сама `LaunchActivity` **осталась объявлена** с `exported="false"` и без единого intent-filter — не выброшена целиком, потому что ~36 мест в телеграмном коде (фоновые сервисы, виджеты, геолокация) строят на неё явный `Intent(context, LaunchActivity.class)`; удалить компонент из манифеста полностью значило бы уронить эти пути `ActivityNotFoundException`. `OpenChatReceiver`/`OpenAttachedMenuBotReceiver` по той же причине не удалены, а переведены в `exported="false"` (у них живые внутренние вызовы из `NotificationsController`/`MediaDataController`, но никакого intent-filter не было и раньше — просто закрыли лазейку «другое приложение может явным `Intent` запустить компонент по имени класса»). **Отдельная ловушка, которую этим чуть не подловили**: `ApplicationLoader.onCreate()` при каждом запуске звал `LauncherIconController.tryFixLauncherIconIfNeeded()` — она проверяет состояние всех alias'ов иконок через `getComponentEnabledSetting()`, а этот вызов **кидает `IllegalArgumentException` на необъявленном компоненте**. Останься вызов — приложение падало бы на каждом холодном старте сразу после удаления alias'ов. Вызов убран из `ApplicationLoader`. `BubbleActivity`/`ExternalActionActivity` (Android bubbles, Telegram Passport) сознательно не тронуты — самые связанные с остальным кодом (16 и 5 внешних упоминаний), решили не трогать в этот заход. Проверено живьём: `adb shell cmd package resolve-activity -c android.intent.category.LAUNCHER` отдаёт ровно одну активность (`SteamDebugActivity`), `resolve-activity` на `https://t.me/durov` больше не называет наш пакет. |
| **codebase-memory не стартует** — `DACL entry grants mutation rights to untrusted identity` | Сервер намеренно отказывается работать, если в его кэш может писать посторонняя учётка (риск подмены индекса). Было: `CodexSandboxUsers` + два осиротевших SID имели Modify на `%USERPROFILE%\AppData` и `%USERPROFILE%\.cache`. Убрано 30.08.2026, бэкап прав с командой отката: `%USERPROFILE%\acl-backup-before-cbm-fix.txt`. Если ошибка вернётся — снова почистить ACL этих папок до SYSTEM/Администраторы/владелец. |
| Скрап steamcommunity.com для аккаунта с vanity-URL иногда падает с `FileNotFoundException` | `HttpURLConnection` с `instanceFollowRedirects=true` (по умолчанию) не умеет сам пройти 302 с `/profiles/{id}/...` на `/id/{vanity}/...` — падает на редиректе, хотя обе ссылки по отдельности отдают 200 (проверено curl'ом). Решено: `instanceFollowRedirects=false` + вручную читать `Location` и переоткрывать соединение (`SteamWebProfile.kt`, `get()`). Редирект ловили не только на голом `/profiles/{id}/`, но и на `/badges/` — непостоянно, между запросами с разницей в секунды, так что чинить надо в одном общем `get()`, а не точечно под один путь. |
| `NetworkOnMainThreadException` изредка при открытии чата/профиля | `getMessageHistory()`/`sendMessage()`/фоновый `requestFriendInfo()` в `getProfileStats()` звали методы JavaSteam (синхронный сокет-I/O) прямо на диспетчере вызывающего кода — а вызывают их из `SteamChatFragment`/`SteamProfileFragment` на `Dispatchers.Main`. Кидало не всегда (похоже, тайминг активации StrictMode нестабилен между холодными стартами), поэтому баг долго не проявлялся живьём. Решено: обернуть каждый вызов в `withContext(Dispatchers.IO)` в `JavaSteamService.kt`. |
| **`adb uninstall` стирает сохранённую сессию логина** | Сделано один раз ради «чистого» обновления иконки лаунчера (подозрение на кэш иконки в лаунчере) — стёрло `EncryptedSharedPreferences` с refresh-токеном, вход слетел, автоматически не восстановить: Android auto-backup сознательно не покрывает эти префы (раздел 9). Для обновления APK всегда `install -r` (как весь остальной день до этого), не `uninstall`+`install` — иконка лаунчера обновляется и от `-r`, специально стирать данные ради иконки не нужно. |
| `Theme.getSelectorDrawable(true)` красит состояние покоя сплошным `key_windowBackgroundWhite`, не прозрачным | На строке/плашке прямо на обычном белом `root` незаметно, но на чём-то с собственным цветом (например, `cardBackground()`) даёт видимое пятно другого оттенка поверх — не видно по чтению кода, поймано только живьём (`SteamProfileFragment`, `buildRow`/`buildStatTile`). Решение — `getSelectorDrawable(false)`: прозрачный в покое риппл, работает и на обычном фоне, и на кастомном, единая логика без ветвления по контексту. |
| **Ложный ANR на холодном старте после долгой dev-сессии на Spike36** (`Telegram Beta isn't responding`) | Не баг кода — `adb shell top -n 1` показал своп эмулятора забит под завязку (1.35 из 1.5 ГБ при 2 ГБ RAM), похоже на накопленный мусор долгой сессии (старые `hprof`-дампы, фоновая активность Play Store/GMS). Решение: убить `emulator.exe`+`qemu-system-x86_64.exe` (`Stop-Process`) и перезапустить обычной командой раздела 3 — диск AVD не трогается, сессия логина не слетает, это не `wipe-data`. Диагностика в сторону: `adb shell ping 8.8.8.8` даёт 100% потерь **даже когда сеть реально работает** — `dumpsys connectivity` (там `EVER_VALIDATED&IS_VALIDATED`) надёжнее, ICMP через NAT эмулятора просто не форвардится, это не индикатор сломанной сети. |

## 5. Что уже работает (проверено на реальном Steam-аккаунте)

- Логин по username/password + Steam Guard (подтверждение в мобильном приложении).
- **Сохранение сессии** между перезапусками (refresh-токен в Keystore-шифрованных
  `EncryptedSharedPreferences`, `resumeSession()` без повторного Guard).
- Список друзей с реальными аватарками (грузятся со Steam CDN), именами, онлайн-статусом.
  Собственный аккаунт из списка исключён (Steam шлёт `PersonaStateCallback` и на себя тоже).
- Отправка и получение сообщений в реальном времени.
- История переписки с сервера Steam (`requestMessageHistory`) — переживает перезапуск.
- Пузыри сообщений, ripple-фидбэк на нажатии, иконка приложения и сплэш.
- Тёмная тема (Telegram «Dark Blue») активируется в `SteamDebugActivity`.
- **Единый экран профиля** (`SteamProfileFragment`) — свой и чужой профиль это один и тот же
  фрагмент, `isOwn` (сравнение с `observeCurrentUser()` при создании) включает/выключает строки,
  для которых у клиентского протокола Steam данные есть только по своему аккаунту (счётчик
  друзей, группы, шестерёнка настроек). Открывается тапом по шапке чата (чужой) или иконкой в
  шапке списка чатов (свой, временная точка входа до нижней навигации). Раскладка шапки — крупная
  (156dp, увеличена с исходных 104dp по просьбе пользователя — маленькой казалась) скруглённо-
  квадратная аватарка слева, имя (26sp)/статус/Steam ID (с мелкой иконкой копирования) справа от

      скриншоты цвета фона а должны быть цвета плашки»), не по чтению кода.
  - **«О себе»** — отдельная карточка (синяя жирная подпись + текст статус-цитаты), раньше был
    плавающий курсивный текст без подписи. Скрыта, пока нет `statusText`. Пользователь поймал
    живьём «не всегда подгружается» — источник (`?xml=1`) фейлится независимо от страницы значков
    (тот же троттлинг steamcommunity.com), но фолбэк-кэша у `statusText` не было вообще, в отличие
    от значков — теперь есть, тоже поле `CachedBadges`/`PrefsBadgesCache` (раздел 5, ниже). У
    `currentGame` такого фолбэка сознательно нет и не будет — устаревшая «сейчас играет» была бы не
    просто протухшей, а реально неверной информацией в момент, когда человек уже вышел из игры.
  - **Значки, статус-цитата, XP-прогресс, счётчик скриншотов и «сейчас играет» — всё вытащено со
    страниц steamcommunity.com,** не по клиентскому протоколу (`SteamWebProfile.kt`, без новых
    зависимостей — голый `java.net.HttpURLConnection`, целевые регэкспы, покрыто юнит-тестами на
    реальной вёрстке). Три разных публичных эндпоинта одного и того же профиля, дёргаются
    параллельно и **всегда все три, каждый раз** (не «пропустить, если значки уже закэшированы» —
    см. ниже, почему):
    - `?xml=1` (легаси, но живой и стабильный формат) → `summary` (статус-цитата) и
      `inGameInfo/gameName` (текущая игра). Путь к `inGameInfo` сверен по исходнику реального
      потребителя этого эндпоинта (`stefkiourk/steam-profile-information` на GitHub), а не
      захвачен живьём — тестовые аккаунты не получилось поймать в момент игры.
    - `/badges/` (не главная страница профиля — там только превью на 2-4 значка) → **все** иконки
      значков (`data-delayed-image`, не `src` — там 1×1 заглушка) и XP-прогресс.
    - `/profiles/{id}/` (обычная страница профиля) → счётчик скриншотов (см. выше).
    Иконка текущей игры — не отдельный запрос, а прямой URL по appid из `inGameInfo/gameLink`:
    `cdn.akamai.steamstatic.com/steam/apps/{appid}/header.jpg`, этот путь стабилен для любого
    приложения в Steam. Раньше «сейчас играет» шло через `PersonaStateCallback` + отдельный вызов
    `store.steampowered.com/api/appdetails` для резолва имени по appid — оба убраны: колбэк не
    гарантирует, что вообще пришлёт игровые поля (`GameDataBlob`) в рамках сессии, а второй вызов
    добавлял ещё одну сетевую SPOF на пути показа «играет».
  - **Кэш значков переживает перезапуск приложения** (`BadgesCache` в `steamchat-domain`,
    `PrefsBadgesCache` — обычный, не шифрованный `SharedPreferences` в TMessagesProj, тот же
    DI-паттерн, что `SessionStore`/`EncryptedSessionStore`) — по прямой просьбе пользователя
    («что бы они не подгружались каждый раз»). Но это **кэш-фолбэк, а не условие пропуска
    запроса**: XP-прогресс живёт на той же странице `/badges/`, что и значки, и обновляется только
    реальным запросом — если использовать кэш как повод не ходить за свежими данными (как было
    сначала), XP просто никогда больше не появится после первой успешной загрузки любого профиля.
    Кэш используется, только когда сам запрос не удался (**Steam троттлит повторные запросы к
    одной странице — живьём словили HTTP 429 после плотного тестирования**); statusText/
    currentGame/XP не кэшируются вообще (не должны протухать в рамках одной открытой сессии).
  - **Живая проверка:** уровень/группы/друзья по-прежнему приходят по клиентскому протоколу
    (`mergePersona()` — трогает поле `SteamUser` только если оно реально есть во флагах
    конкретного `PersonaStateCallback`, старый код затирал всё целиком при каждом колбэке, из-за
    чего гас уже полученный аватар/статус). `getProfileStats()` запускает `fetchLevel()`/веб-фетч
    параллельно (`coroutineScope`+`async`) — раньше шли последовательно, и медленный HTTP-запрос
    держал даже не зависящий от сети кружок уровня. Друг реально переключил игру между тестами
    (Dota 2 → Wallpaper Engine) — карточка и иконка обновились без переоткрытия приложения. После
    фикса кэша-фолбэка XP-бар подтверждён живьём («478 XP до след. уровня», ~20% заливки, цвет по
    бракету уровня). Свайп по строке значков подтверждён в обе стороны — набор видимых иконок
    меняется на каждый свайп (сначала свежий скриншот, потом обратный свайп — снова другой набор).
  - **`SteamUser.game: SteamGamePresence`** (`Unknown`/`NotPlaying`/`Playing(appId, gameId, name,
    richPresence)`) заменил плоский `gameName: String?` — различает «мы ещё не знаем, играет ли
    он» (`Unknown`) от «Steam явно сказал: не играет» (`NotPlaying`), раньше оба выглядели
    одинаково как `null`. Старый `mergePersona()` гейтил игровое состояние по
    `EClientPersonaStateFlag.GameExtraInfo` (код **256**) — реальный баг, живьём подтверждённый:
    Steam шлёт отдельные, более узкие колбэки с `GameExtraInfo`, но без игровых полей вообще, и
    старая проверка принимала их как повод перечитать (пустой) `gameName`, из-за чего висело
    «играет в Dota» уже после выхода из игры. Игровые поля (`gameName`/`gameId`/`gameDataBlob`)
    реально обновляются под `GameDataBlob` (код **512**) — другой бит, подтверждено не по памяти,
    а компиляцией пробника прямо против jar (`EClientPersonaStateFlag.values().forEach { it.code()
    }`). `gamePresence()` (`SteamMapping.kt`) берёт appId из `cb.gamePlayedAppId` (прямое поле
    `game_played_app_id`), **не** из `cb.gameId.appID` — `GameID` бывает мод/ярлык/P2P-файл
    (`isMod()`/`isShortcut()`/`isP2PFile()`), бит-разбор `.appID` у таких может вернуть число, не
    являющееся настоящим Steam appid → битая CDN-картинка; `gamePlayedAppId` в этих случаях честно
    0. Партиальные апдейты: без `GameDataBlob` игра не трогается вообще (даже если пришёл
    Offline/Invisible-статус — `Playing(Dota)` осознанно переживает переход в офлайн, это
    легитимное внутреннее состояние, не баг); `RichPresence` без `GameDataBlob` обновляет только
    `richPresence` у уже существующего `Playing`, не создаёт игру из воздуха. UI обязан сам гасить
    показ «Играет» при `status == OFFLINE` (`steamStatusPresentation()`, раздел «Экран чата» выше)
    — иначе офлайн-друг с сохранённым `Playing` навсегда светился бы зелёным. 10 юнит-тестов
    (`JavaSteamServiceTest`, на настоящих `PersonaStateCallback` из реального protobuf-билдера, не
    моках) на все переходы, включая явно `EPersonaState.Invisible`, не только `Offline`.
  - **`SteamWebDataSource`** (`steamchat-steamkit/SteamWebDataSource.kt`) — интерфейс,
    формализующий уже существовавшую границу между веб-снапшотом (`fetchWebProfile`/
    `fetchNameHistory`, были голыми top-level функциями) и клиентским протоколом:
    `JavaSteamService` теперь принимает его через конструктор (`internal constructor` с полным
    набором параметров + публичный делегирующий с дефолтом на `RealSteamWebDataSource`, чтобы
    существующие вызовы типа `SteamServiceHolder` не заметили изменения). Клиентскую половину
    (login/friends/messages/`mergePersona()`) в отдельный класс **не** выносили — это один
    цельный, уже проверенный, тяжело-стейтфул поток колбэков без внешних потребителей кроме
    самого `JavaSteamService`, разбивать его ради симметрии было бы рефакторингом ради
    рефакторинга. `SteamService` (в `steamchat-domain`) — уже готовая граница repository/UI, ни
    одного типа JavaSteam в контракте (см. doc-комментарий в самом файле); отдельного
    `SteamRepository` заводить не стали, дублировало бы то же самое под другим именем.
  - **Анимированная рамка аватарки** — Points Shop-косметика, у большинства аккаунтов не надета.
    Первая версия рендерила её статичной картинкой (в Android нет встроенного декодера APNG) и
    заодно добавляла анимированный фон шапки профиля через `VideoView`; пользователь оба решения

    анимироваться по-настоящему, не статично.
    - **Источник — `<img src>` внутри `profile_avatar_frame` на странице `/badges/`** (та же
      страница, что уже даёт значки и XP, а не третий отдельный HTTP-запрос, как было в первой

      `<source media="(prefers-reduced-motion: reduce)">` — сознательно не используется, это

      парсером — сначала разобрали реальные `fcTL`-чанки скачанного файла и увидели, что кадры не
      простая смена целиком: часть кадров — маленькие частичные регионы (11×14, 15×11px и т.п.),
      которые компонуются поверх предыдущего кадра (`blend_op`/`dispose_op`), то есть правильный
      декодер — это не «few lines», а реальный риск тонкой ошибки. Библиотека выбрана осознанно:

      minSdk 21 (совпадает с проектом), точка расширения `ByteBufferLoader` — ровно то, что нужно
      для уже скачанных самостоятельно байт (см. `SteamProfileHeaderView.fetchBytes`/

      штатного `Drawable.Callback`, чтобы анимация реально перерисовывалась покадрово), автоплей
      из коробки. Живьём подтверждено, что реально идёт покадрово: скриншоты с интервалом в секунду
      дают разные MD5.

      **только когда рамка реально надета** (`applyDecorations`), иначе у всех остальных профилей
      без рамки макет остался бы пиксель-в-пиксель как был. Статус-точка при этом переносится к
      настоящему углу аватарки, а не к углу рамки.
    - **Персистентный кэш** — `avatarFrameUrl` теперь поле `CachedBadges`/`PrefsBadgesCache` (тот же
      фолбэк-кэш, что уже был у значков, а не отдельный): раз он приходит с той же страницы
      `/badges/`, что и значки, отдельная запись не нужна — один фейл фетча, один фолбэк на всё.

      getProfileStats()` мёржит «свежее, иначе то, что было в кэше» по каждому полю отдельно
      **до** вызова `badgesCache.put()` — сам `put()`/`PrefsBadgesCache` пишет то, что дали,
      без всякой условной логики внутри.
    - **Грабли по пути** (раздел 4): `HttpURLConnection` не смог сам пройти редирект на vanity-URL,
      и три вызова JavaSteam в другом месте кода падали `NetworkOnMainThreadException` — оба
      найдены и исправлены при живом тестировании этой фичи, не были багами самой фичи.
  - **История ников** — маленькая стрелка «▾» справа от имени (тот же жест, что `namehistory_link`
    на настоящей странице профиля Steam), тап открывает диалог со списком прошлых имён и датой
    смены. Источник — не клиентский протокол и не HTML-скрейпинг, а тот же JSON-эндпоинт, который
    дёргает сам JS настоящей страницы профиля (`ShowAliasPopup`): `GET
    /profiles/{id}/ajaxaliases/` → `[{"newname":"...","timechanged":"..."}]`, без авторизации,

    `WebRtcAudioTrack` (форк Telegram, `org/webrtc/audio/WebRtcAudioTrack.java`) играет с
    `USAGE_VOICE_COMMUNICATION`/`CONTENT_TYPE_SPEECH`, то есть в поток `STREAM_VOICE_CALL` — а его
    настоящий телефон по умолчанию отдаёт **в разговорный динамик у уха**, а не в громкий. У
    эмулятора выхода всего один и разговорного динамика нет вообще, поэтому там баг не
    воспроизводится в принципе. Первая версия выбирала speaker **один раз, до создания
    `AudioDeviceModule`**; этого мало: старт `AudioTrack` с voice-communication заставляет систему
    заново пересчитать маршрут и может сбросить выбранное раньше устройство, а `setMode()`
    вдобавок применяется асинхронно. Теперь маршрут **переустанавливается ещё раз после принятия
    звонка**, когда звук уже реально идёт. Заодно: `acquire()` больше не вызывается на
    `Dispatchers.Main` (там же блокирующий `setMode()` — это был риск ANR); громкость
    `STREAM_VOICE_CALL`, если она ровно 0, поднимается до половины (качелька громкости двигает
    этот поток только во время звонка, то есть заранее пользователь его поднять не может, и звонок
    молчал бы при любом маршруте); в диалог выводится реальное состояние — какое устройство
    выбрано, громкость, есть ли аудио-фокус и **пришёл ли вообще входящий поток**
    (`onAddStream`), чтобы «не слышно» можно было отличить от «звук не доехал» за один тест; и
    добавлена кнопка «Динамик» — ручное переключение динамик/ухо прямо во время звонка

    делает сам `VoipAudioManager` в Telegram).

    `NotifyUserLeftVoiceChat`), и дважды мимо. Решил только замер: временно залогировали

    неверным: когда один кладёт трубку, звонок заканчивается у всех.** Поэтому сессия
    останавливается вместе с ним, и это нормальное завершение (`hangup`), а не ошибка. Отдельно:

  - Это всё ещё **пробник исходящего foreground-звонка**, а не готовая продуктовая функция.
    Для выпуска нужны входящий сценарий, нормальный экран звонка, foreground service, audio focus,
    mute/speaker/Bluetooth, remote hangup, reconnect и жизненный цикл Activity. Но главный риск
    снят: протокол, Opus, микрофон, воспроизведение и реальный Steam-собеседник проверены живьём.
    Реализацию продолжать стоит; оценивать её теперь нужно как обычную Android-фичу среднего/
    большого размера, а не как неизвестный reverse-engineering проект.

- **Экран чата приведён к макету** (`SteamChatFragment`/`SteamChatHeaderView`/`SteamMessageCell`)
  — по референс-скриншоту реального мобильного приложения от пользователя:
  - **Шапка** — компактные аватарка+точка статуса+имя+статус прямо в `ActionBar` (сам `ActionBar`
    — обычный `FrameLayout`, поэтому `addView()` работает без специального API), не текстовый
    `setTitle()`. Отступ слева **52dp** и `WRAP_CONTENT`/`MATCH_PARENT` — не подобраны на глаз, а
    списаны с того, как настоящий `ChatActivity.java` добавляет свой `avatarContainer` на
    `actionBar` (`addView(avatarContainer, 0, LayoutHelper.createFrame(WRAP_CONTENT, MATCH_PARENT,
    Gravity.TOP|LEFT, 52, 0, 52, 0))`) — не форк `ChatAvatarContainer` (тот, как и весь
    Telegram-чат, типизирован прямо на `TLRPC.User`/`TLRPC.Chat`, раздел 1), а свежий компактный
    вью на тех же примитивах, что `SteamDialogCell`. Логика текста статуса
    («Играет: X» / «В сети» / «Не в сети», офлайн гасит даже сохранённое `Playing`) вынесена в
    общую `steamStatusPresentation()` (`SteamStatusText.kt`) — раньше жила только в
    `SteamProfileHeaderView`, теперь одна реализация на оба места.
  - **Разделитель дат** («Сегодня»/«Вчера»/иначе `d MMMM`) — `RecyclerView` с двумя типами строк
    (`ChatRow.Message`/`ChatRow.DateSeparator`), список пересчитывается целиком при каждом
    изменении (`buildChatRows()` + `notifyDataSetChanged()`), не точечный `notifyItemInserted` —
    проще и без риска рассинхронизации индексов ради чата, где сообщения не сыпятся потоком.
  - **Пузыри** — галочка «отправлено» на исходящих (`msg_check_s`), **одна, не двойная**: у
    классического friend-message протокола JavaSteam **нет сигнала «прочитано»** вообще
    (`FriendMsgCallback` — только `sender`/`entryType`/`message`, проверено по JAR) — двойная
    галочка была бы выдуманным статусом «прочитано», которого проект не знает. Сообщение только
    из эмодзи рендерится крупнее — `Emoji.fullyConsistsOfEmojis()`, та же утилита настоящего
    `ChatMessageCell`, не самодельный regex (юникодные эмодзи через surrogate-пары руками
    надёжно не разобрать).
  - **Панель ввода** — скрепка честная заглушка-тост «Пока в разработке» (см. ниже, почему), не
    молча нерабочая кнопка. Эмодзи-пикер и звонок (1:1) — уже не заглушки, см. ниже. Плейсхолдер
    поля — «Написать сообщение...» на русском (было захардкожено английское «Message»/«Send»).
  - **Разведка «отправка картинок» / «звонки» / «группы»** (по прямой просьбе пользователя,
    перед реализацией, не вслепую) — раздел 6, таблица ниже.
- **Главный экран (нижняя навигация + список чатов) приведён к макету** от пользователя.
  - **`SteamBottomNavView`** — 4 вкладки (Чаты/Друзья/Настройки/Профиль), не 5 из исходного текста
    ТЗ раздела 6 ниже — пользователь прислал новый макет с 4, макет главнее старого текста.
    Живёт в `SteamDebugActivity`, не внутри стека фрагментов: отдельный `LinearLayout` под
    `actionBarLayout` (`weight=1` на сам `actionBarLayout`, бар фиксированной высоты снизу).
    Вкладка «Чаты» — сумма `unreadCount` по всем `observeDialogs()`, посчитана в `SteamDebugActivity`
    напрямую, не через фрагмент — бар переживает переключение вкладок, а фрагмент экрана чатов
    каждый раз создаётся заново (см. ниже), считать badge внутри него означало бы терять счётчик
    при каждом свайпе на другую вкладку.
  - **Один общий стек фрагментов, не четыре независимых.** Переключение вкладки —
    `removeAllFragments()` + `addFragmentToStack(новый экран)` + `showLastFragment()`: каждый раз
    свежий экземпляр экрана, без сохранения прокрутки/состояния между заходами на вкладку. Осознанное
    упрощение (4 отдельных back-stack'а ради сохранения состояния — заметно больше работы за
    сомнительную для MVP пользу), явно взвешено, не забыто.
  - **Видимость бара — по глубине стека, не по типу фрагмента.** Бар виден только когда
    `fragmentStack.size <= 1` и верх стека — не `SteamLoginFragment` (иначе он мелькал бы и на
    экране логина, где стек тоже глубиной 1). Отступ снизу под жестовую полосу переезжает на то
    из двух view (бар или `actionBarLayout`), что сейчас реально нижнее — компенсация вычисляется
    вместе с видимостью в одной функции `updateNavState()`, не двумя независимо не всегда
    согласованными местами.
  - **Грабли: панель навигации не появлялась вообще никогда, с самого первого запуска.** Не
    флуктуация — воспроизводилось стабильно, включая на чистом эмуляторе с здоровой памятью
    (отдельно исключили ложный след от известной грабли «своп забит» из этой же таблицы — своп
    был здоровый, 230MB из 1.5GB, панель всё равно не появлялась). Причина: `updateNavState()`
    изначально вызывался из `actionBarLayout.viewTreeObserver.addOnGlobalLayoutListener` —
    казалось бы, надёжно, «случается и на push, и на pop». На деле нет: снятый живьём через Toast
    диагностик (`println`/`logcat` в этой сессии повторно оказались ненадёжны — см. грабли про
    голосовой звонок — Toast сработал сразу) показал `size=2, top=SteamDialogsFragment` **уже
    после того, как список чатов полностью отрисовался**. Настоящая причина —
    `ActionBarLayout.presentFragmentInternalRemoveOld()`: при анимированном переходе (обычный
    случай, не только `!needAnimation`) старый фрагмент не убирается из `fragmentsStack` сразу, а
    только после анимации, и делает это через `View.removeViewInLayout()` — метод, **специально
    не вызывающий новый layout-проход** (он расчитан на использование изнутри уже идущего). Из-за
    этого `addOnGlobalLayoutListener` успевал сработать **один-единственный раз**, ровно в момент
    начала перехода логин→чаты, застав старый и новый фрагмент одновременно в стеке
    (`size=2`) — и больше никогда не перевызывался, когда `SteamLoginFragment` реально исчезал
    позже. Настоящий надёжный сигнал «переход (включая его анимацию) действительно завершился» —
    `BaseFragment.onBecomeFullyVisible()`, тот самый хук, который сам `ActionBarLayout` вызывает
    в конце каждого presentFragment/pop-пути. Решено заведением общего `SteamBaseFragment`
    (все экраны `org.steamchat.ui` теперь наследуются от него, не от `BaseFragment` напрямую) с
    единственным переопределённым методом — пробрасывает `onBecomeFullyVisible()` в
    `SteamDebugActivity.onFragmentBecameFullyVisible()` → `updateNavState()`. Старый
    `addOnGlobalLayoutListener` оставлен как дешёвая подстраховка на случай изменений раскладки
    без перехода фрагмента (например, инсеты), но теперь не единственный источник правды.
  - **`SteamDialogsFragment`**: фиксированные вкладки «Все чаты/В сети/Группы» живут в одном ряду
    с уже готовыми пользовательскими папками (`PrefsChatFolders`, отдельная, сделанная ранее фича)
    — специально не единая модель: `SteamDialogsTab` (sealed, `All`/`Online`/`Groups`/`Custom`)
    отдельно от `SteamChatFolder`, чтобы «Все чаты» нельзя было случайно переименовать или удалить
    через UI управления папками, которое работает только с настоящими `SteamChatFolder`. «В сети» —
    локальный фильтр по `friend.status == ONLINE` поверх уже отфильтрованного папкой списка, без
    новых сетевых вызовов. Иконка бренда в шапке (`ic_steamchat_brand.png` в `drawable-nodpi`) —
    копия исходника иконки лаунчера из `TMessagesProj_App`, продублирована руками в ресурсы
    `TMessagesProj`: `org.telegram.messenger.R`, на который ссылается наш Kotlin-код, генерируется
    из ресурсов **библиотечного** модуля `TMessagesProj`, а не модуля приложения (обратная
    видимость невозможна в принципе — зависимость идёт `App → TMessagesProj`, не наоборот).
  - **`SteamFriendsFragment`/`SteamSettingsFragment`** — новые вкладки. У «Настроек» реальна только
    кнопка «Выйти» (`SteamService.logout()`, он уже существовал) — «Тема»/«Уведомления»/«О
    приложении» честные заглушки-тосты, тот же принцип, что скрепка в чате.
  - **Три экрана-вкладки (`SteamDialogsFragment`/`SteamFriendsFragment`/`SteamSettingsFragment`)
    не показывают стрелку назад** — при новой архитектуре они всегда корневые (никогда не
    выталкиваются поверх чего-то ещё), а стрелка пыталась бы вызвать `finishFragment()` в стек
    глубиной 1, что по `needCloseLastFragment` **закрывает всё приложение**. `SteamProfileFragment`
    двузначен (он же и вкладка «Профиль», он же экран чужого профиля, вытолкнутый поверх чата) —
    решается не отдельным флагом в конструкторе, а проверкой в самом `createView()`:
    `parentLayout?.fragmentStack?.size != 1` — если фрагмент внизу пустого стека, он и есть вкладка,
    стрелки не будет; если стек глубже, это обычный вытолкнутый экран, стрелка остаётся. Поймано не
    чтением кода, а живым тестом (см. грабли ниже).
  - **Иконки нижней навигации подобраны и проверены глазами** (тот же контрольный лист через
    Pillow, что и раньше в проекте — растровым именам верить нельзя): `msg_discussion` (Чаты),
    `msg_groups` (Друзья, не `msg_filled_menu_users` — тот же смысл, но другая толщина линии,
    визуально не сочетался с остальными тремя), `msg_settings` (Настройки, уже было проверено
    раньше), `msg_contacts` (Профиль).
  - **Грабли (раздел 4): `LayoutHelper.createLinear(width, height, gravity, ...)` с буквальным
    `0` вместо гравитации.** Не опечатка в проверке типов — компилируется, просто `0` это валидный
    `Gravity.NO_GRAVITY`, а не «не задано» (сентинел для «наследовать от родителя» — это `-1`,
    отдельная константа). Явно переданный `0` **перебивает** гравитацию родителя и прижимает
    дочернюю view к верху её ячейки. Живой симптом: иконка бренда (32dp) в шапке рисовалась
    наполовину под статус-баром, а заголовок «SteamChat» рядом — на своём месте, потому что заголовок
    добавлялся через 2-аргументный `createLinear(width, height)` без гравити вообще (наследует
    `CENTER_VERTICAL` от родительского `LinearLayout`), а иконка — через 7-аргументный с явным `0`.
    Правило на будущее: либо не указывать gravity в `createLinear`, либо указывать реальный, никогда
    не «заполнитель» `0`.
  - **Грабли, та же семья, что уже была на профиле (раздел 4, `getSelectorDrawable(true)`
    красит непрозрачно).** `SteamDialogCell` (личные чаты) годами использовал
    `Theme.getSelectorDrawable(true)`, а `SteamGroupDialogCell` (группы, сделан позже, уже с
    учётом этого правила) — правильный `false`. Пока весь экран был на обычной телеграмной теме,
    разницы не было видно (непрозрачная заливка совпадала с `Theme.getColor(key_windowBackgroundWhite)`
    фоном). После перекраски экрана чатов под `SteamPalette.chatBackground` (тёмная тема экрана,
    не темы приложения) непрозрачная заливка личных строк осталась на СТАРОМ цвете темы —
    видимый разнобой поймал пользователь живьём: строки групп сливались с фоном и пустым местом
    под списком, личные строки — заметно светлее. Починено (`false`), сверено пиксельно
    (`(22,32,45)` = `#16202D` — group/root/gap/nav-bar теперь совпадают ровно). Правило на
    будущее: `getSelectorDrawable(true)` безопасен только там, где фон экрана — обычный
    `Theme.getColor()`, а не собственная палитра — при любой перекраске экрана под свою тему
    проверять все `getSelectorDrawable(true)` на нём.
  - **По прямой просьбе пользователя весь этот класс багов закрыт структурно, не точечно.**
    `SteamPalette.kt` теперь начинается с doc-комментария, явно называющего обе параллельные
    системы цвета в `org.steamchat.ui` (`SteamPalette` — свой тёмный стим-стиль на экранах
    чатов/звонка/нижней навигации/друзей; `Theme.getColor()` — обычная телеграмная тема на
    профиле/играх/настройках/группах) и правило для новых экранов: один экран — одна система, не
    смешивать. Внутри палитры разложено по секциям (фон/текст/пузыри/поле ввода/звонок/presence)
    комментариями-заголовками — те же поля, тот же порядок, просто видно, что к чему относится.
    Добавлен `SteamPalette.rowSelector()` — единственная точка выбора риппла для ячеек, всегда
    прозрачная в покое; **все** 14 мест в `org.steamchat.ui`, где раньше был прямой вызов
    `Theme.getSelectorDrawable(...)` (в т.ч. 3 оставшихся `true` — `SteamGameCell`,
    `SteamProfileHeaderView` ×2, safe по случайности, а не по гарантии), переведены на него. Теперь
    `Theme.getSelectorDrawable` во всём `org.steamchat.ui` встречается только один раз — внутри
    самого `rowSelector()` — так что вопрос true/false физически больше негде решить неправильно.
  это MVP-2 по разделу 21 ТЗ.
- `SteamDebugActivity` — хост нижней навигации и общего стека фрагментов, не финальная навигация
  в смысле «это temporary Activity, которую когда-нибудь заменят на LaunchActivity-интеграцию»,
  но сама структура (бар снизу + один стек) уже не одноразовая заглушка.

## 6. Видение продукта (макет от пользователя)

Тёмная тема, тёмно-синий фон (~`#0E1621`), синий акцент, три экрана с общим нижним меню
из 5 вкладок: **Чаты · Друзья · Игры · Уведомления · Ещё**.

**Экран 1 — Чаты.** Заголовок «SteamChat», справа иконки поиска и нового сообщения. Ряд
вкладок-фильтров: «Все чаты / Друзья / Группы» (активная — синяя таблетка). Список: круглая
аватарка со статус-точкой (зелёная — в сети, оранжевая — отошёл/не беспокоить), жирное имя,
серый превью последнего сообщения, время справа сверху, синий круглый бейдж непрочитанных.
Есть групповые чаты (иконка группы) и боты (значок верификации).

**Экран 2 — Чат.** Шапка: стрелка назад, маленькая аватарка, имя + зелёный подзаголовок
«В сети», справа меню «⋮». По центру — чип-разделитель даты («Сегодня»). Входящие пузыри
тёмно-серые слева, исходящие синие справа; время внутри пузыря снизу справа, у исходящих —
двойная галочка прочтения. Сообщение только из эмодзи — крупнее обычного. Картинки —
скруглённым превью с временем поверх. Внизу: скрепка, скруглённое поле «Написать
сообщение...», иконка эмодзи.

**Экран 3 — Профиль.** Заголовок «Профиль» + шестерёнка. Крупная аватарка со статус-точкой,
имя, «В сети», строка «Steam ID: …» с кнопкой копирования. Две карточки в ряд: «Уровень»
(крупная цифра + прогресс-бар XP «2 350 / 3 500 XP») и «Значки» (число + иконки значков).
Карточка «Сейчас играет» с иконкой игры и статусом («Dota 2 — В главном меню»). Ниже
список-меню со строками и шевронами: Мой профиль Steam · Игры · Друзья (127) · Группы (14) ·
Скриншоты · Настройки.

### Доступность данных Steam для этого макета (проверено по JAR JavaSteam 1.8.0)

| Что нужно | Статус |
|---|---|
| Аватарки, имена, онлайн-статус, «сейчас играет» | ✅ подключено (`PersonaStateCallback`, флаго-зависимый merge — раздел 5) |
| Уровень Steam | ✅ подключено — сырой protobuf `CMsgClientFSGetFriendsSteamLevels` через свой `ClientMsgHandler` (`FriendsLevelsHandler`, нет типизированной обёртки в JavaSteam) |
| Список игр | ✅ подключено — `Player.getOwnedGames()` (генерированный RPC-стаб) |
| Группы (счётчик, только свой аккаунт) | ✅ подключено — `SteamFriends.getClanCount()` |
| Значки, статус-цитата, «сейчас играет» (имя+иконка) | ⚠️ **не через клиентский протокол** — нет bulk-вызова в `Player` для значков, нет вызова для bio-текста, а `PersonaStateCallback` для игры не гарантирует прийти с игровыми полями (`GameDataBlob`) в рамках сессии открытия профиля. Подключено в обход: `steamcommunity.com/profiles/{id}/` (HTML, значки) + `?xml=1` (статус, текущая игра) — раздел 5. Работает только для публичных профилей, с оглядкой на троттлинг Steam. |
| Эмодзи Steam — рендер `:name:` в тексте | ✅ подключено — не через клиентский протокол, прямой CDN-URL (раздел 5) |
| Эмодзи Steam — пикер разблокированных эмоций для отправки | ⚠️ есть `CPlayer_GetEmoticonList_Request` (не подключено) |
| Входящие сообщения в реальном времени | ✅ подключено, но **не** старым `FriendMsgCallback` — сессия логинится с `ChatMode.NEW_STEAM_CHAT` (это нужно звонкам), а в этом режиме Steam шлёт unified-уведомление `FriendMessagesClient.IncomingMessage` (`CFriendMessages_IncomingMessage_Notification`), и легаси-колбэк не приходит вообще. Живой симптом ошибки: в чате пусто, сообщения появляются только после перезапуска приложения (через историю). Поле `local_echo` = наше собственное сообщение, отправленное с другого клиента (десктопа) — кладём его как исходящее и без счётчика непрочитанных. |

8. **Отправка картинок в чате** — больше не "недокументировано, ловить по трафику": нашёлся
   полный реальный рабочий пайплайн в исходниках `node-steamcommunity` (актуальная, живая
   Node.js-библиотека для Steam-ботов, `components/users.js`, метод `sendImageToUser`) — не
   документация, а код, который реально работает у множества ботов. Три шага:
   1. `POST https://steamcommunity.com/chat/beginfileupload/?l=english` (multipart:
      `sessionid`, `l=english`, `file_size`, `file_name`, `file_sha` (SHA1 hex), `file_image_width`,
      `file_image_height`, `file_type=image/jpeg|png|gif`) → JSON `{success, hmac, timestamp,
      result: {ugcid, url_host, url_path, use_https, request_headers[]}}`.
   2. `PUT` сырые байты картинки на `(use_https?https:http)://{url_host}{url_path}` с заголовками
      из `request_headers` (подписанный URL облачного хранилища, не сам Steam).
   3. `POST https://steamcommunity.com/chat/commitfileupload/` (multipart: `sessionid`, `l`,
      `file_name`, `file_sha`, `success=1`, `ugcid`, `file_type`, `file_image_width`,
      `file_image_height`, `timestamp`, `hmac` — оба взяты из ответа шага 1, `friend_steamid`,
      `spoiler=0|1`) → JSON с финальным `result.details.url` — именно эту ссылку и шлют потом
      обычным текстовым сообщением (что подтверждает уже сделанный `SteamMessageContent.Image`:
      `images.steamusercontent.com` уже распознаётся и превращается в карточку с реальной
      картинкой, раздел 5 — рендер стороны получателя уже готов и ждёт только сторону отправки).
   Всё ещё блокирует реализацию: **`sessionid`/`steamLoginSecure` cookie** — аутентифицированной
   веб-сессии в проекте по-прежнему нет (`WebAPIUserNonceCallback` есть в JavaSteam, но обмен
   nonce → cookie не реализован), плюс multipart/PUT-запросов в `HttpFetch.kt` тоже нет (там только
   простые GET). Не начинать без отдельного запроса — веб-сессия + мультипарт + HMAC-пляска это
   отдельный, немаленький кусок работы, но теперь он полностью специфицирован, а не «неизвестно».
9. **1:1 звонки другу** — технический риск снят живым тестом: web-CM unified RPC + встроенный
   WebRTC/Opus дают двусторонний голос с настоящим Steam-клиентом (раздел 5). Следующий этап —
